# Concurrency

md2html runs on one thread. Rendering, `--check`, `--watch` (a loop on the main thread that looks at the inputs' times of change a few times a second, `watch.rs`) and the EPUB writer share nothing. `--pdf` starts Chrome as a child process and waits for it with a time limit of 90 seconds, then kills it (`export/print.rs`). The one place with threads is the local server.

There is no async code in the workspace and no async runtime, in md2html or in the tooling.

## The server

`md2html --serve` (`serve.rs`) renders and watches on the main thread, accepts connections on one thread of its own, and answers each connection on a thread of its own.

| Thread | Owner, and who waits for it | How it ends | How its failure is seen |
| --- | --- | --- | --- |
| main | the process | the inputs are gone for five seconds (exit 66), the listener fails (exit 74), or Ctrl-C | the run's exit code and message |
| `md2html-serve`, the listener's | `serve::serve`, in a thread scope: it is joined before `run` returns | the site is closed, and a connection of the server's own wakes it out of `accept`; or 50 failed accepts in a row | its error is the run's (`the server stopped: ...`, exit 74); a panic is `the server stopped unexpectedly` (exit 70) |
| `md2html-answer`, one per connection | the listener's thread, in a scope of its own; it keeps each thread's handle with a handle on its connection (`serve/listener.rs`) | its answer is written; its time limits (below); or the server closing: a read waits for the browser in slices of 100 ms and looks between them whether the server is closing, and the listener's thread shuts the connection, which on macOS and Linux also ends a write waiting on a browser that stopped reading | an error is a trouble told on the next look at the files; a panic is joined and told as a trouble; after the close, neither is a trouble |

- **What is shared.** One `Site`, on `run`'s stack and borrowed by every thread, which all end before it does: the rendered pages, the render count and whether the server is closing in a `Mutex<State>`; a `Condvar` the reload signals wait on; the time and size limits (`Limits`, read only); and the connection troubles not yet told, in a `Mutex<Vec<String>>` of at most 100. There is no `Arc` and no atomic: the number of open connections is the number of connection threads the listener's thread has not yet waited for, and only it counts them.
- **A lock is held for a copy or a swap, never across work.** The main thread renders first and takes the lock only to put the new pages in, in one assignment, then wakes the reload signals after letting go (`Site::publish`). A request takes the lock to copy one page out and writes it to the socket after letting go. A reload signal waits on the condition variable (which lets go of the lock while it waits) for at most 15 seconds at a time, copies the render count and lets go before it writes. Closing takes the lock to set one flag.
- **A poisoned lock is not a second panic.** A thread that stopped while holding the pages left them whole, because they are replaced in one assignment and the other fields are numbers and a flag set in one; the next thread takes them as they are (`PoisonError::into_inner`). No `lock()` result is unwrapped.
- **The number of threads is bounded.** At most 64 connections are served at once (`Limits::SERVE`). A connection beyond the limit is told the server is busy (503), on the listener's thread, with a write limit of one second so that a slow browser cannot hold the listener, and closed; it is not read first, so its browser may see the connection reset instead of the answer.
- **Every connection is bounded in time and in what it can make the server read.** A request has 10 seconds to arrive whole, however slowly it is sent; a write may wait 10 seconds for the browser; a line of the request is at most 8 KiB, its end included, and at most 64 headers are read. A reload signal ends after 10 minutes, and the page asks for a new one by itself. After a refusal, what the browser still sends is read and thrown away for at most one second and 64 KiB, so that the refusal is not lost to a reset.
- **A request is read whole or refused with the status that says why** (`serve/request.rs`, RFC 9112): 400 for what is not a request (a request line that is not `METHOD target HTTP/1.x`, a target in neither form a server is sent, a header that is not one, a space before a header's colon, a folded line, no `Host` or two, a request that ends before its empty line), 408 when its 10 seconds run out after it began, 414 for a request line over 8 KiB, 431 for a header over 8 KiB or more than 64, 505 for an HTTP other than 1; then 403 for a request not addressed to this machine, 405 for a method other than GET and HEAD, 404 for what is not served. A connection that asks nothing in its 10 seconds is closed without an answer (a browser opens some ahead).
- **No busy waiting.** The main thread sleeps 250 ms between looks at the files; the listener's thread waits in `accept`; a reload signal waits on the condition variable; a connection's thread waits in a read, 100 ms at a time, or a write with a time limit. The only loop that tries again without waiting for an event is the wake-up of the listener's thread at the close, which pauses 100 ms between tries and ends when the thread does.
- **How it stops.** When the inputs are gone (or the listener fails), `serve` closes the site: no connection is taken any more and every reload signal ends at once. It wakes the listener's thread with a connection of its own; that thread shuts every open connection, waits for every connection's thread and ends; `serve` waits for it. A connection's thread waiting for the browser to send sees the close within 100 ms on every system: it waits in slices with `peek`, which takes nothing, so a slice that runs out loses no byte, and the 10 seconds of the request are kept across the slices. It does not rely on the shut connection to wake it, because Windows does not end a read blocked on another thread when the connection is shut. A write blocked on a browser that stopped reading is ended by the shut on macOS and Linux; on Windows it ends by its own limit, 10 seconds, the one wait the stop can take there. Nothing is left running or holding a socket when `run` returns. The close is made by a guard that is dropped on a panic of the main thread too, since a thread scope waits for its threads even then: a render that panicked would otherwise leave the server waiting forever instead of ending. Ctrl-C is not caught (the standard library has no signal API, and a handler would need `unsafe` or a dependency): it ends the process, and the operating system closes the listener and every connection. The server writes nothing to disk, so either way nothing is left half done.

Enforced by: `significant_drop_tightening` and `significant_drop_in_scrutinee` (a lock guard lives no longer than its use), `mutex_atomic`, `rc_mutex` and `clone_on_ref_ptr` in `Cargo.toml`, at deny; `unwrap_used` and `expect_used` for the lock results. Checked by: in `src/serve/request/tests.rs`, `a_request_is_read_as_it_is_sent`, `a_malformed_request_is_answered_400` and `a_request_over_its_limits_is_refused_with_its_status`; in `src/serve/tests.rs`, `the_reload_signal_says_the_render_and_ends` and `the_reload_signal_ends_when_the_server_closes`; over real connections in `src/serve/tests/tcp.rs`, `refusals_reach_the_browser_whole`, `a_slow_request_is_answered_408_and_a_silent_one_closed`, `connections_beyond_the_limit_are_turned_away` `the_server_stops_with_connections_open_and_leaves_nothing_behind` (a silent connection, half a request and a reload signal open, the server stopped in well under every one of their limits, each connection ended, no trouble kept), `a_panic_in_the_run_stops_the_server`, `a_read_waiting_on_a_silent_browser_ends_when_the_server_closes` (nothing shuts the connection; the read ends on the close alone) and `a_connection_closed_both_ways_reads_as_its_end` (macOS refuses to set a time limit on such a connection; the reader takes that as the end). `tests/browser/live.js` (CI job `browser`) runs the server and checks that a saved change reloads the page within two seconds, keeping the reader's place, and that a path outside the document's folder is not served. What the server promises is in [SECURITY.md](../../SECURITY.md), guarantee 5.

## The tooling

The pipeline behind `just go` and `just ship` (`scripts/ci-pipeline`) is plain functions, with no async code and no runtime. Every child process it starts has a time limit (`src/child.rs`): a step an hour (`--timeout`), `du` half a minute, a question asked on this machine (`git`, `rustc -vV`, `df`, `sccache`, a tool's `--version`) a minute, and the two that go over the network (`gh pr list`, `cargo update`) five minutes. The child's output is read on two scoped threads while its exit is polled every 50 ms, so a child that fills a pipe never stalls; past the limit it is killed and waited for, and the caller gets an error that names the program and the limit (`captured`, `finished`) or `None` (`output_within`). A killed `cargo` can leave a `rustc` behind that holds the pipe: the readers wait for it to close, so the return is late but nothing is lost; killing a process group needs a signal the standard library does not send. The parallel validation stage runs its commands on a fixed number of scoped worker threads, which take the next command from a shared atomic index and start no new one after the first failure (`src/exec.rs`).

Scoped threads are joined before their scope ends, so every thread has an owner that waits for it, and a thread that panics is reported as an error by the code that joins it, not lost. Shared state between them is atomics, not locks.

Two places run children without a time limit, on purpose: the developer tools (`just use-local`, `just release-local`: `cargo install`, `zip`, the built binary's `--version`), which a person runs and watches, and for which no limit would be right for every machine (Ctrl-C ends them); and the build scripts' `git` and `rustc --version` (`md2html-version`), local queries that neither prompt nor use the network. md2html itself runs one child, Chrome for `--pdf`, polled every 100 ms and killed and waited for after 90 seconds (`export/print.rs`).

The lints for async code stay at deny, so the rule holds the day async code arrives: a lock guard, a `RefCell` borrow or an `Rc` does not live across an `.await` (`await_holding_lock`, `await_holding_refcell_ref`, `await_holding_invalid_type`), and a function that never awaits is not `async` (`unused_async`).
